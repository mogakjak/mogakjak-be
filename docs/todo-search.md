# 할 일 검색 API (#102)

## 요청과 응답

`GET /api/todos/search?keyword=ㄱㅂ&limit=20&cursor=<UUID>`

인증된 사용자 소유의 삭제되지 않은 할 일을 검색한다. 삭제된 카테고리와 소유권이 잘못된 카테고리도 제외한다. 완료 여부와 할 일 날짜는 제한하지 않아 과거 작업도 다시 선택할 수 있다.

- keyword: 생략 시 빈 문자열, 최대 35 UTF-16 코드 단위(할 일 제목 검증과 동일).
- limit: 기본 20, 1~100. 빈 값·정수가 아닌 값·범위 초과는 400.
- cursor: 생략 가능. 직전 응답의 nextCursor를 사용한다. 잘못된 UUID, 타인/삭제된 할 일/삭제된 카테고리의 커서는 400. 검색어가 바뀌면 커서를 초기화한다.
- 정렬: 생성 시각 내림차순, 동일 시각은 UUID의 DB 바이너리 순서 내림차순.
- 빈 검색어 및 앞뒤 공백만 있는 검색어: 전체 목록 조회.
- 결과 없음: items=[], hasNext=false, nextCursor=null.
- 응답: 기존 ApiResponse의 data 안에 items, hasNext, nextCursor. items는 {todo, category}이며 #101 상세 조회와 DTO를 공유한다. todo에는 id/task/date/targetTimeInSeconds/actualTimeInSeconds/progressRate/lastWorkedAt 등이 포함된다.
- 목표시간이 없으면 targetTimeInSeconds/progressRate는 null. actualTimeInSeconds/progressRate는 저장된 누적값 기준이다. 실행 중 시간까지 포함한 상세 값과 공개 설정은 선택 후 `GET /api/todos/{todoId}`로 조회한다.
- lastWorkedAt은 #100의 작업 이력 기준 ISO 8601(+09:00), 작업 이력이 없으면 null. 상대 날짜 표시는 프론트가 처리한다.
- 추가 결과가 있을 때만 hasNext=true이고 nextCursor는 마지막 반환 항목 ID이다. 커서 항목이 삭제되면 목록을 처음부터 다시 조회한다.

## 매칭 규칙

제목과 검색어를 Unicode NFKC 정규화하고 영문은 소문자로 비교한다. 검색어 앞뒤 공백만 제거하며 내부 공백과 특수문자는 그대로 유지한다. 정규화된 제목에서 연속된 부분 문자열을 찾는다.

| 검색어 | 매칭 | 매칭하지 않음 |
| --- | --- | --- |
| ㄱ | 가방, 공부, 각본 | 나무 |
| ㄱㅂ | 가방, 각본 | 가 방 |
| 가 | 가방 | 각본 |
| 가ㅂ | 가방 | 각본 |
| ㄱ ㅂ | 가 방 | 가방 |
| 가 / ㄱㅏ | 가방 (가로 정규화) | 각본 |
| % / _ / .* | 해당 문자를 실제 포함한 제목 | SQL 와일드카드/정규식으로 해석하지 않음 |

현대 한글 초성 19개(쌍자음 포함)를 지원한다. 독립 모음은 문자 그대로 비교한다. NFKC로 정규화되는 호환/분해 자모와 전각 영문도 지원하며, 지원하지 않는 옛한글 자모는 문자 그대로 비교한다. 문자열 처리는 코드 포인트 단위여서 이모지 서로게이트 쌍을 쪼개지 않는다.

## 조회 및 성능

초성 파생 컬럼을 저장하지 않으므로 기존 데이터 초기화나 제목 수정 동기화가 필요 없다. 기존 제목을 즉시 검색한다.

사용자/삭제 여부/생성 시각/ID 복합 인덱스 `idx_todo_user_deleted_created`를 추가한다. 후보는 ID·제목·생성 시각만 256개씩 keyset 방식으로 조회하고 애플리케이션에서 매칭한다. limit+1개를 찾으면 중단한다. 반환할 항목만 카테고리 fetch join으로 조회하고 최근 작업 시각은 두 개의 집계 쿼리로 일괄 조회한다. 항목마다 카테고리/작업 이력을 조회하지 않으며 COUNT/OFFSET 쿼리도 사용하지 않는다.

이 인덱스는 소유권 필터와 정렬/커서를 돕는 인덱스이지 초성 텍스트 인덱스가 아니다. 드문 검색어나 결과가 없는 경우 사용자 전체 제목을 순회할 수 있어 최악 시간 복잡도는 O(사용자의 활성 할 일 수)다. 후보 메모리는 배치 크기로 제한한다. 사용자당 수만 건 이상 또는 지속적인 검색 지연이 관찰되면 파생 검색 인덱스나 전문 검색 저장소를 검토한다. 초기 소규모 데이터에 맞춘 구현이며, 전체 데이터량에 무관한 검색 시간을 보장하지 않는다.

개발 환경은 기존 ddl-auto=update 정책에 따라 배포 시 인덱스가 생성된다. 컬럼 추가·값 변경·백필은 없으며 기존 목표시간 nullable 변경과 별개다. 대량 데이터 환경에서는 인덱스 생성 비용을 별도로 검토한다.

## 프론트 연동

입력 debounce, IME composition 이벤트, 이전 요청 취소/늦은 응답 무시는 프론트 책임이다. ㄱ → 가처럼 조합 중 문자열도 서버가 현재 문자열 기준으로 검색할 수 있다. 작업 선택 후 상세 조회로 사이드바를 구성하며, 목표시간은 기존 값을 불러오고 수정/해제할 수 있다.

## 검증

초성 19개·완성형·혼합·공백·IME·특수문자·이모지 매칭, API 입력 검증, 서비스 배치/일괄 조회 및 실제 MySQL의 소유권·삭제 필터·UUID 커서·256개 초과 후보·제목 변경·작업 이력/인덱스를 테스트한다.

MySQL 테스트는 `ISSUE102_MYSQL_URL`이 loopback의 전용 `issue102_verify` DB일 때만 실행한다. 운영/개발 DB를 테스트 대상으로 사용하지 않는다.
